# Architecture

[日本語](architecture.ja.md)

## Overview

```
                 clients
        ┌───────────┼───────────┐
        ▼           ▼           ▼
   AWS (ALB)   Google (LB)  Azure (App Gateway)
        │           │           │
   ECS: API    Cloud Run: API  Container Apps: API     CLOUD_ID = aws / google / azure
        │  reads    │  reads    │  reads
        ▼           ▼           ▼
   RDS / Aurora  Cloud SQL   Flexible Server          PostgreSQL 18, schema "app"
        └──── logical replication (full mesh, over site-to-site VPN) ────┘

   writes: every API → the primary database (one of the three, over the VPN)
```

- The same container image runs on every cloud. `CLOUD_ID` tells each
  instance which cloud (node) it is on.
- Each API **reads** from its own cloud's database and sends **writes** to
  the primary database, whichever cloud that is.
- The databases replicate every change to each other with PostgreSQL native
  logical replication, so every cloud can read every row.
- Networks, VPN, private DNS, databases, container services and CI/CD are
  created by the infrastructure repository (`cdktn_multicloud_backend`).

## Data model

Replicated tables live in schema `app`. Every table has:

| Column | Purpose |
| --- | --- |
| `id uuid` | Generated by the database (`gen_random_uuid()`) |
| `owner_cloud text` | Cloud whose API created the row (informational) |
| `version integer` | Incremented on every update; used for optimistic locking |
| `created_at`, `updated_at` | Timestamps |

`app.write_journal` (replicated) records every write transaction: epoch
and node of the primary, mutation name, arguments, result, idempotency key
and time. See "Write journal" below.

Schema `ops` is node-local and not replicated: `ops.schema_migrations`
(applied migrations) and `ops.cluster_state` (this node's view of the
primary, below).

## Writes

### Why a single primary

Native logical replication has **no conflict resolution**: a change received
from another node simply overwrites the local row. If two clouds updated the
same row at the same time, each would apply the other's change and the
databases would keep different values without any error. Locks do not help:
they exist only inside one database.

So all writes go to one database, the **primary**. On it, row locks,
optimistic locking (`version`) and multi-statement transactions work as on
any single PostgreSQL. The other databases receive the changes through
replication.

### Which node is the primary

Each node stores, in `ops.cluster_state`, its own name, the primary's name
and an **epoch** (incremented on every switchover). `scripts/switchover.sh`
sets it. Each API reads the state of every node every
`PRIMARY_REFRESH_INTERVAL_MS` and uses the primary of the **highest epoch**
it can see. The epoch never goes back, so a node that comes back with an old
state does not mislead the APIs.

### A write transaction

```
BEGIN; SELECT ops.assert_primary(<epoch>)                  -- 1 round trip
  [; SELECT … FROM app.write_journal WHERE idempotency_key = …]
<the statements of the mutation>                            -- 1 round trip each
INSERT INTO app.write_journal …; COMMIT;
  SELECT ops.wait_for_peers(<n>, <timeout>)                 -- 1 round trip
```

1. `ops.assert_primary` fails unless the node is the primary of that epoch
   (`PRIMARY_UNAVAILABLE`; the API looks up the primary again). It takes a
   share lock on the state row, so a switchover waits for running writes.
2. After `COMMIT`, `ops.wait_for_peers` waits until at least
   `WRITE_ACK_PEERS` other nodes have **flushed** everything written so far
   (`confirmed_flush_lsn` of their replication slots). The subscriptions use
   `synchronous_commit = on`, so this takes about one round trip between the
   clouds plus a few milliseconds.
3. Only then does the API report success. If no other node confirms within
   `WRITE_ACK_TIMEOUT_MS`, the API returns `COMMIT_UNCONFIRMED`: the write is
   committed on the primary but may be lost if the primary fails now.

Every confirmed write therefore exists on at least two clouds, and a primary
that is cut off from the others cannot confirm anything.

Each statement sent from an API in another cloud costs one round trip
between the clouds. Keep mutations to few statements.

### Write journal and idempotency keys

Every write transaction inserts one row into `app.write_journal`, in the
same transaction and the same round trip as `COMMIT`. Because the table is
replicated, it moves with the data during a switchover.

- **Idempotency keys.** With `idempotencyKey`, the first round trip also
  looks the key up. If it is there, nothing runs: the API checks that the
  operation and arguments are the same (`IDEMPOTENCY_KEY_REUSED`
  otherwise), waits for the confirmation like a new write, and returns the
  stored result. Two concurrent writes with the same key: the unique index
  makes the second wait for the first and then return its result.
- **Recovery.** `scripts/journal-diff.sh` lists the writes one node has and
  another does not, with their arguments and results, e.g. an old
  primary's unconfirmed writes before it is reset.
- **Retention.** `scripts/journal-prune.sh` deletes old rows on the primary
  (30 days by default), which is also how long keys work.

### Switchover

`scripts/switchover.sh` moves the primary (see
[operations.md](operations.md#switchover)):

- **Planned** (the old primary is reachable): the old primary gets the new
  epoch first and stops accepting writes; the script waits until the target
  has flushed everything; then the other nodes get the new epoch. Writes
  fail for about a second (`PRIMARY_UNAVAILABLE`).
- **Forced** (the old primary is down or cut off from the other databases,
  `--force`): if the old primary is still reachable from the script, it is
  fenced first. On every other reachable node, the subscription from the
  old primary is disabled, so that its unconfirmed writes cannot arrive
  later and overwrite newer data, and the new state is set. The target must be the node that received the most
  from the old primary. The old primary must be reset before it rejoins.

Changes received from another node are not forwarded (`origin = none`). If
the surviving nodes received different amounts from the old primary, the
ones that received less miss those writes and must be reset (the script
warns).

## Replication

Set up by `scripts/replication-setup.sh` for every pair of nodes in
`NODES`:

- Each node publishes every table in schema `app` as publication `mc_pub`.
- Each node subscribes to every other node:
  `mc_sub_<publisher>_to_<subscriber>`.
- `origin = none`: a node does not forward changes it received from another
  node, so changes do not loop.
- `copy_data = false`: subscriptions do not copy existing rows (except when
  seeding a new node with `SEED_FROM`).
- `synchronous_commit = on`: the subscriber flushes each applied
  transaction at once, so the primary's confirmation is fast.

DDL is not replicated. Each migration is applied to every node by
`scripts/migrate.sh`, which records it in `ops.schema_migrations`.
The publication publishes inserts, updates and deletes only: `TRUNCATE` is
not replicated (use `DELETE` for data that must disappear everywhere).

The subscriptions' connection strings (with the replication passwords) are
updated by `scripts/replication-setup.sh` whenever they change.

## Database roles

| Role | Created by | Purpose |
| --- | --- | --- |
| admin | the cloud (infrastructure repository) | Runs migrations, replication setup and switchovers |
| `app_api` | `scripts/api-role-setup.sh` | The API's connection: `SELECT, INSERT, UPDATE, DELETE` on schema `app`; `EXECUTE` on the `ops` functions only |
| `app_repl` | `scripts/replication-setup.sh` | Used by the other nodes' subscriptions |

The `ops` functions are `SECURITY DEFINER`: the API role needs no access to
the `ops` tables or to replication statistics.

## Configuration

Environment variables, read by `src/config.ts`; see
[.env.sample](../.env.sample) and the README. Each API needs the connection
settings of every node (`DB_*` for its own, `DB_<NODE>_*` for the others in
`PEER_NODES`). On the clouds, the container platform sets them and passwords
come from each cloud's secret store.

## Build and deployment

Each cloud builds the same `Dockerfile` with its own CI/CD:

| Cloud | File | Deploys to |
| --- | --- | --- |
| AWS | `buildspec.yml` (CodeBuild) | ECS (Blue/Green) |
| Google Cloud | `cloudbuild.yaml` (Cloud Build) | Cloud Run |
| Azure | `azure-pipelines.yml` (Azure Pipelines) | Container Apps |

The build stage runs `npm test`, so a failing test (including a missing
migration or an outdated `generated/schema.graphql`) stops the build before
any cloud deploys it. The pipelines pass the commit as `APP_VERSION`, which
the health endpoints return. A new version becomes ready (`/readyz`) only
when its migrations are applied to that cloud's database
(`src/migrations.ts`), so the platforms keep the old version serving when
the database update was forgotten.

The pipelines, their triggers and their variables are created by the
infrastructure repository.
