# Model definitions

[日本語](models.ja.md)

Each table of the API is defined by one YAML file in `models/`. From these
files the API builds, at startup, the GraphQL types, queries and mutations;
`npm run generate` writes the SQL migrations and a printout of the GraphQL
schema.

## Workflow

1. Add or edit `models/<name>.yaml`.
2. Generate:

   ```bash
   npm run generate
   ```

   - `migrations/NNNN_<change>.sql`: SQL for what changed since the last
     generated migration (compared with `migrations/models.snapshot.json`).
   - `generated/schema.graphql`: the resulting GraphQL schema, for review.

3. Review both files, then test locally (README, "Local testing"):

   ```bash
   docker compose run --rm tools scripts/migrate.sh
   docker compose run --rm tools scripts/replication-setup.sh   # new tables only
   docker compose up -d --build
   ```

4. Commit the YAML, the migration, the snapshot and the printout together.
   `npm test` fails if a migration or the printout is missing.
5. On the clouds: `scripts/migrate.sh`, then `scripts/replication-setup.sh`
   for new tables, then deploy the API ([operations.md](operations.md#schema-changes-migrations)).

`npm run generate -- --check` changes nothing and fails when a migration or
the printout is missing (for CI).

## Example

```yaml
# models/order.yaml
name: Order                     # GraphQL type; queries order / orders
description: A customer order.
fields:
  title:    { type: string, required: true, maxLength: 200 }
  status:   { type: enum, values: [draft, ordered, shipped], required: true, default: draft }
  amount:   { type: decimal, min: 0 }
  dueOn:    { type: date }
  memo:     { type: string, description: Free text. }
  meta:     { type: json }
indexes:
  - fields: [status, createdAt]
list:
  defaultLimit: 50
  maxLimit: 100
  filterable:
    status: [eq, in]
    amount: [gte, lte]
    memo: [ilike, isNull]
  sortable: [amount, dueOn, createdAt]
  defaultOrder:
    - { field: createdAt, direction: desc }
```

## Model

| Key | Required | Description |
| --- | --- | --- |
| `name` | yes | GraphQL type name, PascalCase (`Order`) |
| `plural` | no | List query name; default: English plural of the name in camelCase (`orders`, `categories`) |
| `table` | no | Table in schema `app`; default: snake_case of `plural` (`orders`, `order_lines`) |
| `description` | no | Shown in the GraphQL schema |
| `fields` | yes | The model's fields (below) |
| `indexes` | no | Additional indexes (below) |
| `relations` | no | Relations to other models (below) |
| `bulkWrite` | no | Updates and deletes by condition (below) |
| `queries` | no | Named read-only SQL queries (below) |
| `list` | no | Settings of the list query (below) |

Every model also gets these fields; do not define them:

| Field | Column | Type | Description |
| --- | --- | --- | --- |
| `id` | `id` | `ID!` | UUID generated by the database |
| `ownerCloud` | `owner_cloud` | `String!` | Cloud whose API created the row |
| `version` | `version` | `Int!` | Incremented on every update; pass it back to update / delete |
| `createdAt`, `updatedAt` | `created_at`, `updated_at` | `String!` | ISO 8601 timestamps |

## Fields

Field names are camelCase; the column is the snake_case form (`dueOn` →
`due_on`).

| Key | Description |
| --- | --- |
| `type` | One of the types below |
| `required` | `NOT NULL`. On create it must be given, unless it has a `default` |
| `default` | Value used when the field is not given on create |
| `unique` | Unique constraint |
| `maxLength` | `string`: maximum number of characters |
| `min`, `max` | `int`, `float`, `decimal`: inclusive bounds |
| `values` | `enum`: allowed values (letters, digits, `_`) |
| `description` | Shown in the GraphQL schema |

| Type | PostgreSQL | GraphQL | Notes |
| --- | --- | --- | --- |
| `string` | `text` | `String` | A required string must not be blank |
| `int` | `integer` | `Int` | |
| `float` | `double precision` | `Float` | |
| `decimal` | `numeric` | `String` | Exact numbers as strings, e.g. `"12.34"` |
| `boolean` | `boolean` | `Boolean` | |
| `datetime` | `timestamptz` | `String` | ISO 8601; `default: now` for the current time |
| `date` | `date` | `String` | `YYYY-MM-DD` |
| `uuid` | `uuid` | `ID` | |
| `enum` | `text` + `CHECK` | enum `<Model><Field>` | e.g. `OrderStatus` |
| `json` | `jsonb` | `JSON` | Any JSON value; no default, not unique, not sortable |

`maxLength`, `min`, `max` and `values` are checked by the API and by a
`CHECK` constraint in the database.

## Indexes

```yaml
indexes:
  - fields: [status, createdAt]          # orders_status_created_at_idx
  - fields: [title], unique: true        # orders_title_key
  - fields: [dueOn], name: orders_due    # explicit name
```

Index fields that are used by `filterable` conditions and `sortable` orders
of large tables. The name defaults to `<table>_<columns>_idx` (`_key` when
unique) and must fit in 63 characters.

## List settings

| Key | Default | Description |
| --- | --- | --- |
| `defaultLimit` | 50 | `limit` when not given |
| `maxLimit` | 100 | Largest `limit` accepted |
| `filterable` | none | Field → operators allowed in `where` |
| `sortable` | none | Fields allowed in `orderBy` |
| `defaultOrder` | `createdAt` ascending | Order when `orderBy` is not given; `id` is always added last |

Operators:

| Operator | Meaning | Types |
| --- | --- | --- |
| `eq`, `ne` | equal, not equal | all except `json` |
| `in` | one of a list | `string`, `int`, `float`, `decimal`, `date`, `uuid`, `enum` |
| `lt`, `lte`, `gt`, `gte` | comparisons | `string`, `int`, `float`, `decimal`, `datetime`, `date` |
| `like`, `ilike` | SQL pattern (`%`, `_`), `ilike` ignores case | `string` |
| `isNull` | `true`: no value, `false`: has a value | fields that are not `required` |

Only what is listed can be used: this keeps queries on indexed, intended
columns.

## Relations

```yaml
# models/order.yaml
relations:
  customer: { belongsTo: Customer, required: true, onDelete: cascade }

# models/customer.yaml
relations:
  orders: { hasMany: Order, foreignKey: customer }
```

**belongsTo** (`customer: { belongsTo: Customer }`) adds:

- the field `customerId` (column `customer_id`, type `uuid`), set on
  create / update like any field and usable in `filterable`
- an index on it (unless an index already starts with it)
- a foreign key to `customers.id`
- the GraphQL field `customer: Customer` on `Order`

| Key | Default | Description |
| --- | --- | --- |
| `belongsTo` | | Target model |
| `required` | `false` | `customerId` must be set |
| `onDelete` | `restrict` | When the customer is deleted: `restrict` (refuse while orders exist), `cascade` (delete the orders), `setNull` (clear `customerId`; not with `required`) |
| `description` | | Description of `customerId` |

**hasMany** (`orders: { hasMany: Order, foreignKey: customer }`) adds the
GraphQL field `orders(where, orderBy, limit, offset): [Order!]!` on
`Customer`, with the target's list settings. `foreignKey` names the
`belongsTo` relation on the target. Nothing changes in the database.

Relations are read from this cloud's database. All `customer` fields (or all
`orders` lists with the same arguments) of one request are loaded with one
query, not one per row.

A unique or foreign key violation (e.g. a `customerId` that does not exist,
deleting a customer that still has orders with `restrict`) fails with
`CONSTRAINT_VIOLATION`. Foreign keys are checked on the primary only;
replication applies rows on the other nodes without checking them, so the
order in which rows arrive does not matter.

## Bulk writes

```yaml
bulkWrite:
  update: true      # Mutation.updateOrders(where, input)
  delete: true      # Mutation.deleteOrders(where)
  maxRows: 1000     # default
```

```graphql
mutation {
  updateOrders(where: {status: {eq: draft}}, input: {status: ordered}) { count }
}
```

- `where` uses the model's `filterable` settings (required for bulk writes)
  and must have at least one condition.
- If more than `maxRows` rows match, nothing is written and the mutation
  fails with `TOO_MANY_ROWS`.
- Every matched row gets `version + 1`. The write is one transaction on the
  primary, journaled, and takes an `idempotencyKey` like any write.

## Named queries

Read-only SQL exposed as a GraphQL query, for what the generated queries
cannot do (aggregates, joins):

```yaml
queries:
  orderTotals:
    description: Total amount per status since a time.
    sql: |
      SELECT status, count(*) AS order_count, coalesce(sum(amount), 0) AS total
        FROM app.orders WHERE created_at >= :since GROUP BY status ORDER BY status
    params:
      since: { type: datetime, required: true }
    returns:
      status: { type: string }
      orderCount: { type: int }
      total: { type: decimal }
```

```graphql
{ orderTotals(since: "2026-01-01T00:00:00Z") { status orderCount total } }
```

| Key | Default | Description |
| --- | --- | --- |
| `sql` | | One SQL statement. `:name` is a parameter (bound, never pasted into the SQL) |
| `params` | none | Parameters: `type` (below), `required`, `description` |
| `returns` | | Result columns: `type`, `required`, `description`. The SQL column must be named like the key or its snake_case (`orderCount` or `order_count`) |
| `list` | `true` | `false`: return the first row or `null` |
| `timeoutMs` | 5000 | Statement timeout (at most 60000); `QUERY_TIMEOUT` when exceeded |
| `description` | | Shown in the GraphQL schema |

Types: `string`, `int`, `float`, `decimal`, `boolean`, `datetime`, `date`,
`uuid`, `json` (as for fields). `int` also accepts `bigint` results such as
`count(*)`.

The query runs on this cloud's database in a `READ ONLY` transaction, as the
API role: it cannot write, and it sees only what that role may read. Every
`:name` in the SQL must be declared in `params` and every parameter used.
Write `::type` casts as usual; a literal `:word` inside a string is taken for
a parameter, so pass such values as parameters instead. The SQL is not
checked until it runs: try each query locally.

## Generated API

For `Order`:

```graphql
type Query {
  order(id: ID!): Order
  orders(where: OrderWhere, orderBy: [OrderOrderBy!], limit: Int = 50, offset: Int = 0): [Order!]!
}
type Mutation {
  createOrder(input: CreateOrderInput!, idempotencyKey: String): Order!
  updateOrder(id: ID!, version: Int!, input: UpdateOrderInput!, idempotencyKey: String): Order!
  deleteOrder(id: ID!, version: Int!, idempotencyKey: String): Boolean!
}
```

```graphql
{
  orders(
    where: {status: {in: [ordered, shipped]}, amount: {gte: "100"}}
    orderBy: [{field: amount, direction: DESC}]
    limit: 20
  ) { id title status amount }
}
```

- `where`: all given conditions must match (AND).
- `updateOrder`: omitted fields keep their value; `null` clears a field that
  is not required (for a required field, `null` means unchanged).
- With `relations`, `bulkWrite` and `queries`: the fields, mutations and
  queries described above.
- Writes run on the primary and are journaled; see
  [architecture.md](architecture.md#writes) and the README for
  `idempotencyKey` and the error codes.

## Changes that are generated

- a new model (table and its indexes)
- a new field that is not required, or that has a `default`
- a new `belongsTo` relation that is not required (column, index, foreign
  key); `hasMany` needs no migration
- adding, changing or removing an index
- `description`, `list`, `bulkWrite` and `queries` (no migration; they only
  change the API)

## Changes that are not generated

Removing a model or a field, renaming, or changing a field's type or
constraints can lose data, and with replication it must happen in the right
order on every node. `npm run generate` refuses them. Instead:

1. Write the migration by hand: next number in `migrations/`, e.g.
   `migrations/0007_drop_orders_memo.sql`. Keep it compatible with the API
   that is running: e.g. deploy an API that no longer uses a column before
   dropping it.
2. Update the YAML to match.
3. Accept the new state without generating a migration:

   ```bash
   npm run generate -- --baseline
   ```

The same applies to an existing table that was created by hand
(`migrations/0001_create_items.sql` and `models/item.yaml`).

## Rules from replication

- Every table has the system fields; `id` is a UUID. Do not use sequences
  (their values are not replicated).
- `npm run generate` never truncates or drops a table or a column.
- New tables must be added to replication (`scripts/replication-setup.sh`)
  before the API writes to them.
